[状態遷移図の書き方と使いどころ]({% post_url 2026-06-09-state-transition-diagram-guide %})で、状態遷移図は設計の穴を見つけるツールとして使えると書いた。ただ、図にはひとつ弱点がある。図に現れるのは「書いた遷移」だけで、「書き忘れた遷移」はどこにも現れない。線が1本足りなくても、図としては成立して見えてしまう。

その書き忘れを機械的にあぶり出す道具が状態遷移表だ。図の補完として使うもので、書き方も運用もシンプルなわりに、レビューやテスト設計での効きが大きい。

---

## 状態遷移図と何が違うのか

状態遷移図は、遷移を「線」として描く。つまり存在する遷移の一覧であり、線を引かなかった組み合わせについては何も語らない。

状態遷移表は、縦に状態、横にイベントを並べて、**全組み合わせをセルとして並べる**。存在しない遷移も「空欄」という形で目の前に現れる。状態4つ×イベント5つなら、検討すべき組み合わせは20個だと分母が確定する。図には、この分母がない。

漏れの検出が目的なら、図より表の方が構造的に有利ということになる。

---

## 書き方

手順は3つしかない。

1. 状態をすべて列挙して行にする
2. イベントをすべて列挙して列にする
3. セルを1つずつ埋める

前回の記事で使ったログインセッションの例をそのまま表にしてみる。図に描いた遷移をセルへ写すと、こうなる。

| 状態 ＼ イベント | ログイン操作 | 認証成功 | 認証失敗 | ログアウト操作 | タイムアウト |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 未ログイン | → 認証中 | ？ | ？ | ？ | ？ |
| 認証中 | ？ | → ログイン済み | → 未ログイン | ？ | ？ |
| ログイン済み | ？ | ？ | ？ | → 未ログイン | → セッション切れ |
| セッション切れ | → 認証中 | ？ | ？ | ？ | ？ |

セルに書く値は4種類に決めておく。

| 記法 | 意味 |
| :--- | :--- |
| → 遷移先 | このイベントでその状態へ遷移する |
| −（ハイフン） | その状態ではこのイベント自体が発生しえない |
| 無視 | イベントは発生しうるが、状態は変えないと決めた |
| ？ | まだ検討していない |

最初に図から写した時点では、埋まっていないセルをすべて「？」にしておく。ここからが本番で、「？」を1つずつ「→」「−」「無視」のどれかに変えていく作業が、そのまま漏れの検出になる。

---

## 漏れの見つけ方

上の表では、図にあった7本の遷移が20セル中7つを埋めただけで、13個の「？」が残っている。これを分類しながら潰す。

**「−」にできるもの。** 未ログイン状態で「認証成功」イベントは発生しえない。認証中を経由しない限り、認証APIのレスポンスは飛んでこないからだ。こうしたセルは「−」にして閉じる。

**「無視」と決めるもの。** ログイン済み状態での「ログイン操作」はどうか。UIでボタンを隠すから起きない、と考えたくなるが、それはUI層の話で、状態機械としては「受け取っても何もしない」と決めておく方が安全だ。ここで「UIで防ぐのか、状態機械として無視するのか」を明示的に選ばされるのが表の効能でもある。

**本物の漏れ。** 「認証中」の行を横に見ていくと、「タイムアウト」のセルが「？」のままだ。認証APIがいつまでも返ってこなかったら、この設計では永遠に認証中に留まる。図を眺めていたときには気づかなかった抜けで、`認証中 → 未ログイン（タイムアウト、エラー表示）` の遷移を足す必要がある。同様に「セッション切れ」状態での「ログアウト操作」も未定義だった。切れたセッションでログアウトを押した利用者に何を見せるかは、決めていなければ実装者が現場で即興することになる。

検出が終わったら、埋めた結果をそのまま残す。「−」「無視」「？」を区別して書いてあれば、後から見た人が「検討済みで起こりえないのか、単に考えていなかったのか」を判別できる。全部ただの空欄にしてしまうと、この記録価値が消える。

## テスト設計への接続

埋め終わった表は、そのままテストケースの一覧になる。

- 「→」のセルを一通り実行するのが有効遷移のテスト。すべての遷移を最低1回通すカバレッジを0スイッチカバレッジと呼び、連続する2遷移の組み合わせまで通すと1スイッチカバレッジになる
- 「−」「無視」のセルは無効遷移のテストに使う。「起きないはずの操作が本当に拒否されるか」「無視するはずのイベントで状態が壊れないか」の確認で、この観点は表がないとテスト設計から抜けやすい

ソフトウェアテストの資格体系でも、状態遷移テストはこの表(ステートテーブル)を基に設計する技法として整理されている。

## 図と表の使い分け

役割が違うので、どちらかへの置き換えではない。

| 場面 | 向いているもの |
| :--- | :--- |
| 全体像の説明・オンボーディング | 図 |
| 設計レビューでの議論 | 図（表は手元資料） |
| 漏れの洗い出し | 表 |
| テストケース設計 | 表 |
| 検討結果の記録 | 表（−・無視・？の区別） |

実務での順番は「図でラフに書く → 表へ写して穴を潰す → 確定した遷移を図へ戻す」が扱いやすい。レビューの場で見せるのは図で、そのレビューに耐える裏付けを表で作っておく、という分担になる。

---

## 表が大きくなりすぎたら

状態の爆発は表にも起きる。むしろセル数として即座に跳ね返るぶん、図より早く危険に気づける。20状態×10イベントで200セルになったら、その表は検討にも維持にも耐えない。

対処は図のときと同じ原則で、責務ごとに状態機械を分割する。加えて表ならではの整理として、同じ扱いをするイベントは1列にまとめる、直交する属性（ログイン状態と課金状態など）は最初から別の表に分ける、という手がある。1枚の表は多くても10状態×8イベント程度に収めたい。

---

## まとめ

状態遷移図が「構造を伝える」道具だとすれば、状態遷移表は「網羅を検証する」道具だ。図を書いて満足しそうになったら、一度表へ写してみる。「？」のセルの数だけ、実装時に即興で決められるはずだった仕様が、設計の段階で決まる。
